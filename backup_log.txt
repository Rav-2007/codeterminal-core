    fix(editapply): undo takes back the directories the apply run created
    
    Fix C made undo remove a created FILE instead of restoring its 0-byte
    snapshot. It left the directories that file arrived in standing, so
    undoing "create pkg/sub/deep/thing.go" gave the user back an empty
    three-level tree they never made, while reporting the workspace
    reverted. Same failure class Fix C was written for: the report and the
    disk disagree.
    
    THE DIRECTORIES ARE RECORDED, NOT INFERRED, and that is the whole design
    rather than an implementation choice. "Remove the parent if it is now
    empty" is nearly right and wrong in the one case that matters: a user who
    had already made an empty directory and asked for a file inside it would
    have their directory deleted by an undo that never created it. So the
    apply run writes a created-dirs manifest beside created-files, using the
    same reversible pre-write bookkeeping (Fix 1 ordering) — a write that
    then fails takes the claim back, exactly as it does for created-files.
    
    Three things bound what the removal can touch, and it needs all three
    because a directory removal has no snapshot behind it:
    
      - the set comes from the run's own manifest, so a user's directory is
        never a candidate;
      - every path goes through confinedRestorePath, the same confinement
        the file reverts use, so a hand-edited manifest cannot aim it
        outside the workspace;
      - os.Remove is non-recursive, so a directory holding anything at all
        simply stays — including one holding a file this undo could not
        revert.
    
    It runs only after every file revert has committed, and never after a
    partial failure: removing directories in a tree of unknown state is not
    something to attempt, and relying on ENOTEMPTY to save us would be
    relying rather than deciding.
    
    Neuter-verified twice. Without the removal, "undo left pkg/sub/deep/
    standing". With the manifest swapped for the emptiness heuristic, "undo
    deleted mine/, a directory the user made" — which is the test that
    proves the manifest is load-bearing and not ceremony.

    Gate 6 closed five data-integrity races (100% read-modify-write lost update,
    ~68% backup-session collapse, ~98% undo-guard defeat, ~88% double restore,
    prune-vs-undo) with the daemon's per-workspace sync.Mutex. That lock is
    in-process only, and its own comment justified this with "there is exactly one
    daemon process behind the socket." That premise was false: the CLI (`edits
    apply`/`edits undo`) and the TUI review flow each write the same workspace
    files from their OWN process. Every one of those races therefore reopened
    whenever a CLI or TUI run overlapped a daemon one — normal, legitimate use
    (terminal apply while the IDE is open), not an exotic attack.

    <root>/.codeterminal/apply.lock. flock is released by the kernel on process
    death, so a killed CLI cannot wedge the workspace (an O_EXCL lockfile would
    have needed lock-breaking heuristics and would strand on SIGKILL). Each
    acquisition opens its own fd, so one mechanism covers both the cross-process
    and in-process cases.
    
    Taken INSIDE the three mutation primitives, not at their call sites, because
    the bug being fixed is precisely a caller that forgot to lock:
      editapply.Apply               VerifyUnchanged -> backups -> write
      editapply.NewBackupSessionDir the stat/mkdir mint plus its prune
      daemon.runUndoSession         the guard check through the commit
    Each span is atomic w.r.t. the others, which is all five races need; they need
    not be locked together, since Apply independently re-checks staleness
    byte-for-byte and so refuses rather than clobbers. No span covers a human
    prompt, so a CLI/TUI user sitting on [y/N] never blocks the daemon. The
    daemon's mutex is kept as the in-process fast path; ordering is always mutex
    then flock, so the two cannot deadlock. server_workspace_lock.go's false
    "one process" comment is corrected in place.
    
    Verified: cross-process exclusion proven with two real OS processes (holder
    held 1500ms; a second process blocked 1196ms and acquired exactly on release).
    Tests in editapply/applylock_test.go (lost-update through the real Apply door,
    session-collapse, exclusion, per-root keying) — fail-when-neutered proven: the
    neutered build reproduces the exact lost update ("Apply #1 reported SUCCESS but

    snapshot existed to match it against. Reordered to

    fully determined by PrepareEdit. The snapshot is now recorded before the write
    it describes, so it is taken back (backupAfterReversible) if that write fails
