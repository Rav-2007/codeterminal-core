## 4. The pinning trap: scope sound, judgement inverted

`clients/vscode/src/test/suite/daemonRealSpawn.test.ts`, suite
*"a daemon that cannot start says why, somewhere the extension can read it"*. Before this chunk it
deleted the variable from the environment and asserted the daemon logged
`CODETERMINAL_API_BASE must be set`.

**Has it ever been seen to fail? No — and it could not.** **(M)** In run `34739694099` at `1013e1b`
its test prints as a pass:

```
  the extension can start the daemon it ships
    ✔ a cold workspace spawns a daemon that answers a real handshake (275ms)
    ✔ a second window adopts the running daemon instead of spawning another (263ms)
  a daemon that cannot start says why, somewhere the extension can read it
    ✔ the failure reason reaches the daemon log file
```

The suite's **scope is sound** — the property it names is real, and
`lastDaemonLogLines` in `clients/vscode/src/extension.ts` depends on it. Its **judgement is
inverted**: it reached that property through a fixture that *is* the defect, so fixing the product
would have turned it red. A test that can only fail when the product is repaired is not a test of
the product.

So it was **inverted, not deleted**: the fixture became a structurally invalid base, which
`validateAPIBase` in `daemon/startup_validate.go` refuses by design and always will, and a second
test now asserts the case the file used to certify.

### 4b. The second instance, and it is a different family member

The chunk asked whether any other test has this shape. The sweep
(`git grep -n -E 'must be set|exits with|expects failure' -- '*_test.go'`) returned **one** hit, and
it is a comment, not an assertion **(M)**. But the sweep was looking for the wrong shape.

`daemon/twoworkspaces_test.go`'s `daemonEnv` helper says it outright:

> *"The API base is a dead port ON PURPOSE. … The daemon requires the variable to be set at all,
> which is why it is here."*

That test does not *certify* the defect — it **accommodates** it, and documents the accommodation in
a comment. Three places did this **(M)**:

| Site | What it does |
|---|---|
| `daemon/twoworkspaces_test.go:170` | supplies `CODETERMINAL_API_BASE` to every spawned daemon |
| `clients/vscode/src/test/suite/daemonRealSpawn.test.ts:47` | supplies it, with a comment naming "the defect this file's second suite is about" |
| `clients/vscode/scripts/e3-pilot-test.js:147` | supplies it to the pilot harness |

**The generalisable shape, and it is broader than "a test that certifies the defect":**

> *A defect that every test works around is invisible to all of them.* Certifying it (`assert the
> daemon dies`) and accommodating it (`set the variable so the daemon lives`) are the same failure
> wearing different clothes — both make the defect a fixture. The accommodating form is more common
> and much harder to grep for, because it looks like ordinary setup.

That is the same family as `1013e1b`, which the owner cited: there, a test was green because it won
a race. Here, tests were green because they were all handed the one thing no user has. **In all
three the test passes and the property is untested.** `1013e1b`'s vacuity floor is what caught its
case; nothing here had a floor, because nothing here knew it was measuring a configuration.

## 7. The hole the obvious fix would have opened

The chunk's element 3 is "a `contributes.configuration` block exposing the setting". Contributed at
the default scope, that setting is overridable by `.vscode/settings.json` **inside the workspace** —
so a repository could redirect the daemon's model endpoint to a host it chooses, and the prompt,
which is the user's code, would go there.

This repository already defends that boundary one road over: `neverPassesAWorkspaceSuppliedConfigToTheDaemon`
in `clients/vscode/src/test/suite/daemonBinary.test.ts` exists because passing `--config` from the
workspace was a bug. A contributed setting reaches the same boundary by a different road.

The setting is therefore `"scope": "machine"`, and the check refuses anything else — **committed
before the setting existed**, so the requirement could not be back-fitted to whatever was written.

**A second carve-out, for the same reason.** The default is applied only when *not* in proxy mode.
In proxy mode the key comes from `CODETERMINAL_MOCHIII_KEY` and the proxy's address is
deployment-specific; defaulting there would send a Mochiii key to OpenRouter — a credential
delivered to a host it was not issued for. Measured **(M)**:

```
$ env -i ... CODETERMINAL_USE_PROXY=true ./codeterminal-daemon --workspace ...
exit=1
CODETERMINAL_USE_PROXY is set but CODETERMINAL_API_BASE is empty; the proxy's address cannot be guessed
```

**The default endpoint is not a default credential.** With no key the daemon starts and serves
retrieval, apply, undo and search — which `daemon/startup_validate.go`'s own reasoning says work
fine offline — and reports the provider outcome per request. That is the degraded state the file's
own split is for, and it is strictly better than telling the user "exited 1 5 times".

The value is not invented: `proxy/main.go` has carried this exact constant as `defaultUpstreamBase`
since it was written **(M)**. **The daemon lacking the default its own proxy already had is the
defect, stated in one line.**
