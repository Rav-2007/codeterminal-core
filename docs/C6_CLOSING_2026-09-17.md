## A finding this report produced by checking the gate that checks it

The handover list carried a row reading *"`docs-coderefs` counts 19 enforced
documents where 23 carry the marker"* as a **counting disagreement**. It is not one.
It has a mechanism, and the mechanism is a vacuity hole.

In `scripts/docs-coderefs.sh:93` the citation set is tested for emptiness and the
document is skipped — **before** the enforcement marker is looked at in
`scripts/docs-coderefs.sh:95`. So a document that carries the marker but has no
citation matching the pattern is counted in **neither** total. It is not reported as
enforced, not reported as unenforced, and does not appear in the banner at all.

Derived rather than estimated, and the arithmetic closes exactly:

| | |
|---|---|
| Documents carrying the marker | **24** (`git grep -l`) |
| Silently dropped | **5**, listed: `docs/C5_METHOD_2026-09-15.md`, `docs/C5b_TOPOLOGY_2026-09-15.md`, `docs/C7b_DELIVERY_2026-09-16.md`, `docs/CHECKPOINT_ADDENDUM_2026-09-16.md`, **and this report** |
| Reported as enforced | **19** — and 24 − 5 = 19 |

**The counting disagreement was the symptom.** The defect is that a document leaves
the enforced set silently: reformat its citations — drop the backticks, or write a
path without a `:line` suffix — and the gate stops inspecting it while continuing to
pass. The gate does have a vacuity floor, but it is **global** (zero references
checked across all documents is a failure), and a global floor cannot see one document
going dark while others still carry citations. **This is the enumerated-scope failure
in its vacuity form, inside the gate this pass extended twice.**

`(M)` — measured. **Recommended, not implemented**, and deliberately so: a per-document
vacuity floor changes which runs are red, and the closing chunk's job is to land a
merge, not to alter a verdict surface underneath it. Implementing it would also
immediately fail four existing documents and this one, which is H14's situation
exactly — a rule needing five exemptions at birth. The right shape is probably to
report marker-carrying documents with zero citations as a distinct third category
rather than to fail them, and that is a design decision with a measurement attached,
which is to say the next pass's work and not this one's.

**And it applied to this document.** This report carried the marker while being in the
dropped set, so its marker was a claim the gate did not honour. The two citations
above are real, resolve, and put it in the enforced set — which is the smallest
honest fix and also the reason the finding was found at all.

### The macOS failure, and a third reading

```
--- FAIL: TestSQLiteCancellation_DoesNotReachAnFTS5PhraseMatch (0.25s)
    cancelled at 200ms, the FTS5 match returned after 227.709625ms (under the 1s bar)
    with a genuine context.Canceled -- SQLite now HONOURS the interrupt inside a phrase match.
        This is an improvement, not a failure. Re-measure, then update serveConn's
        cancellation comment.
        IT DOES NOT ON ITS OWN JUSTIFY REMOVING THE LEXICAL BOUND, and the previous
        wording of this message said it might. ...
```

The fork offered was *the test is wrong on darwin* versus *the test found a real darwin
defect*. **Neither.** The test's own doc comment says *"A FAILURE HERE IS GOOD NEWS: it
means a newer SQLite or driver polls the interrupt inside FTS5"* — it is a **premise
tripwire that fired exactly as designed**, and the product on darwin is *better*, not
worse.

What discriminated the readings was reading the test rather than the failure: it
already carries scars from two earlier platform corrections, including a Windows one
where *"the query returned an error after 120.2 ms — before the 200 ms cancel had even
fired"*. So its author had already met platform variance once and guarded it with an
`errors.Is(err, context.Canceled)` skip.

**The defect is the axis the baseline was recorded on.** *"A failure here is good news"*
was written with **time** in mind — a new SQLite version, firing once, reconciled once.
The behaviour turns out to vary by **platform**, and on a platform axis an
unconditional assertion does not fire once. It fires on every run of the platform
where the premise is false, forever, and **nobody can fix SQLite being better.**

| platform | measured |
|---|---|
| linux | ~3.6 s uncancelled; the VDBE loop never polls inside the phrase match |
| darwin | a genuine `context.Canceled` at **227.709625 ms** |
| windows | refuses a 200,000-character phrase before the interrupt is relevant — skipped, and the map is never consulted |

The baseline is now per-`GOOS` and asserted **in both directions**, which is what the
file header already claims of every pair in it. An absent `GOOS` **skips with
instructions** rather than borrowing a default, because an unmeasured platform is not
evidence for either behaviour.

**This cannot weaken the lexical bound, and that was checked rather than assumed.**
`daemon/lexicalbound_test.go` pins `maxLexicalQueryChars` against its own derivation
and asserts refusal in both directions at the boundary, independently of this test. The
failure message now says so, so the next reader does not have to rediscover it.

**And the script already knows.** `scripts/fuzz.sh` prints *"NO crashing input was
recorded -- this is not a fuzzing FINDING"* and *"expected to be intermittent on a busy
runner"*, and then sets `status=1` four lines later. **It computes the right
discriminator and fails against its own classification** — twice now, discarding 25
green jobs on the branch and taking down `main`.

**Recommended, not implemented**, because changing when a gate fails changes what CI
guarantees and that is not a closing chunk's call. The remedy is narrow and in this
repository's own idiom: **pass when there is no crashing input *and* the exec count
clears a vacuity floor; keep failing when execs are zero**, which is the case the
current behaviour actually protects. `(M)`.

## Step D — not run

Step D's grant was conditioned on Step C completing, and this chunk's standing decision
is **no dispatch until the macOS job is green**. `build` is red on `main`, so the
dispatch does not run. It would re-measure a known-red state at roughly sixty billable

## The ordering problem this exposed, which is structural

**A push to a branch does not run macOS.** The matrix is
`(github.ref == 'refs/heads/main' || github.event_name == 'workflow_dispatch')`, so on a
branch it selects Windows only. The failing test was introduced on this branch and had
**never run on macOS** before the merge.

So: **the cheapest place to have caught this is the one place it structurally cannot be
caught**, and the only push that exposes macOS is the irreversible one.

The remedy exists and is cheap: **`workflow_dispatch` enables macOS from *any* ref**, so
one dispatch on the branch would have found this before the merge. And that is exactly
what `scripts/gate-parity.sh:132` hides by claiming macOS runs *"only on main"* — **a
banner inaccuracy filed as cosmetic, whose cost has now materialised as a red `main`.**

It also means **Step 6 as written cannot be executed**: "push the branch, let CI
exercise the macOS matrix" describes something a branch push does not do. Verifying the
fix on macOS before delivering it requires either a dispatch on the branch, or the
fast-forward itself — and those have opposite risks.
