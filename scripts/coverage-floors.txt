# Coverage floors — the ratchet's gate. One line per PACKAGE: <import-path> <floor%>
#
# Enforced by scripts/coverage-ratchet.sh, which runs in CI per module.
#
# These are Phase 0's measured values (docs/ROBUSTNESS_BASELINE.md), not
# aspirations. The rule is RATCHET, DON'T CHASE: a floor may only ever be raised,
# and only to a number that has actually been measured on main. Nobody should
# lower a floor to make a red build green -- that converts the one mechanism that
# noticed a regression into a rubber stamp. Lower it only with a recorded reason
# (a package genuinely losing testable surface, e.g. code deleted).
#
# Keyed by package, not module, because `helper` contains two packages whose
# coverage differs by 68 points; a module-level floor would average that into
# meaninglessness.
#
# Every package MUST be listed. The script fails on a package it has no floor
# for, so a newly added package cannot silently escape the gate -- adding one
# means deciding its floor, even if that decision is 0.0.
#
# Why proxy is 80.3 and not 80.7: the same commit measured both, a run-to-run
# difference on a shared statement count. The floor takes the LOWER reading so
# ordinary variance can never trip the ratchet; only a real drop can.
#
# RAISED 2026-09-02, after the plan-mode / capability / gates batch. Three
# packages were carrying headroom a regression could hide inside: daemon +5.2,
# clients/tui +3.3, helper +1.4. Each measured THREE TIMES UNCACHED
# (`go test -count=1 -cover`) with zero variance across the three -- daemon
# 78.2 x3, clients/tui 82.2 x3, helper 22.2 x3 -- and floored a few tenths
# below, per the take-the-lower-reading rule above.
#
# The tree measured is the one that fast-forwards main in the same batch, and
# CI's own ratchet reported the SAME THREE FIGURES on it, read out of the job
# logs rather than assumed: daemon 78.2, helper 22.2, clients/tui 82.2 (run
# 33596543817, all 25 jobs green). Local and Linux CI agree to the tenth. That
# is what "measured on main" is asking for; it is recorded here because the
# rule above is the only reason these numbers can be trusted at all. No other
# platform measures coverage -- the Windows and macOS jobs vet and cross-build.
#
# 0.2 of headroom is deliberate and is not thin by this file's standard:
# protocol and helper/helperproto sit at +0.0 today. It is affordable only
# BECAUSE the variance is zero across four independent runs; if any package
# ever shows a spread, its floor goes back to a few tenths below the LOWEST
# reading, not below the mode.
#
# ONE CONDITIONAL WORTH KNOWING, from the same CI log: the daemon job warns
# `bwrap CANNOT create a user namespace - sandbox tests will skip and
# daemon/mcp coverage will fall below its floor`. That is a pre-existing
# runner-dependent failure and it names daemon/mcp, which is why daemon/mcp is
# NOT among the three raised here. If it ever turns out to move the top-level
# daemon figure as well, 78.0 is the floor to revisit first.
#
# daemon/mcp (+1.0), editapply (+1.6) and proxy (+1.1) were NOT raised. Their
# headroom is within the range the protocol note below calls ordinary variance,
# and only one reading was taken for editapply and proxy. Raising a floor on a
# single measurement is exactly what the three-run rule exists to prevent.
#
# RAISED 2026-08-01, after the MCP hardening pass. Four packages had drifted
# well above their floors -- daemon +2.1, daemon/mcp +5.7, proxy +5.7, protocol
# +3.4 -- which is unguarded headroom: a regression inside it would not trip
# anything. Each new floor is a few tenths below a value measured three times
# in a row, following the same take-the-lower-reading rule as the note above.
#
# RAISED 2026-08-09, after the cut-off-history fix (b1'/L2) added tests to
# daemon and clients/tui. Both measured identically on three UNCACHED runs
# (`go test -count=1`): daemon 74.3 x3, clients/tui 79.2 x3. Floored a few tenths
# below each (74.0, 78.9), per the take-the-lower-reading rule above.
#
# protocol was NOT raised, deliberately, and the reason is worth recording: the
# same three uncached runs gave 93.3, 93.3, 92.3. A one-point run-to-run swing
# is larger than the 0.5 of headroom above its current floor even at the LOWER
# reading, so raising it would buy a little coverage guard and pay for it in
# ratchet flakes -- and a gate that cries wolf is the one people start passing
# with -count=1 until it goes green. Left at 91.8 until the variance is
# understood. (The first attempt at this measurement read three identical
# numbers because Go had CACHED runs 2 and 3; a cached result is one
# measurement wearing three hats, and would have hidden the swing entirely.)

# 2026-09-03, clients/tui 82.0 -> 83.0. The escape-sanitization work
# (sanitize.go and its four test files) took this package from 82.2 to 83.3.
# Measured THREE TIMES UNCACHED with the test cache cleared before each run:
# 83.3 x3. Floored a few tenths below, like every other entry here, so ordinary
# variance is not a red build. A ratchet that is never raised is a ratchet that
# only ever documents the past.
#
codeterminal/daemon              78.0
